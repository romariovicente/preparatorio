# Publicação do PREPARATÓRIO

O frontend atual usa React/Vite e pode ser publicado como site estático em `https://romariovicente.github.io/preparatorio/`. O código online deve ser construído a partir de `frontend/`; o backend Java histórico não é iniciado por GitHub Pages.

## Separação dos arquivos

Os modelos, texturas e prévias excedem o orçamento de um único site Pages. O manifesto `frontend/src/config/cloudAssetManifest.json` relaciona cada caminho `/assets/...` à URL HTTPS do arquivo publicado em um repositório de acervo. A geometria e os metadados de origem não são alterados por essa resolução. O build Pages exclui `public/` do artefato, copia apenas o ícone pequeno e mantém o artefato abaixo de 900 MiB. Um arquivo marcado `null` no manifesto fica retido do site público; o livro completo, por exemplo, pode permanecer apenas no backup privado até haver autorização para distribuí-lo.

O arquivo Blender editável e os checkpoints são backup de autoria e não precisam ser transferidos ao navegador. Devem ser preservados em destino privado separado, com verificação SHA-256 e uma restauração de teste. Um commit local não demonstra que esse backup já chegou ao GitHub.

## Comandos

```text
cd frontend
npm ci
npm run lint
npm test
npm run test:source
```

`npm test` contém a validação completa e requer os binários locais reais. `test:source` roda apenas os arquivos de testes que não leem arquivos; a CI mostra quantas suítes ficaram para a verificação completa. Essa separação não representa aprovação dos binários que não foram transferidos à CI.

Para construir o site público, configure `VITE_BASE_PATH=/preparatorio/` e `VITE_EXTERNAL_ASSETS_ONLY=true`, gere o manifesto real e execute `npm run build:pages`. O verificador recusa a publicação quando alguma referência de acervo não possui URL HTTPS nem retenção explícita. O workflow executa instalação travada por `package-lock.json`, lint, testes de fonte e esse build antes de publicar. O repositório precisa ter Pages configurado para GitHub Actions.

## Serviço compartilhado e acesso do criador

`multiplayer/server.js` é uma demonstração local em memória: limita sessões, não oferece contas permanentes ou banco de dados, e mantém CORS restrito a localhost. Não foi promovido a servidor público nesta entrega. O frontend publicado não tenta conectar ao computador do visitante: sem `VITE_API_BASE_URL` HTTPS, desativa o transporte compartilhado e continua a exploração individual. O relógio continua derivado do dispositivo até existir uma fonte de tempo configurada; isso não é sincronização validada com um serviço externo Jarvis.

A senha, seu verificador e o token de propriedade não pertencem ao frontend, às variáveis `VITE_`, ao Git público ou aos assets. O acesso privado existente depende de configuração fora do projeto e permanece indisponível em um site somente estático. Uma futura hospedagem do backend exige TLS, CORS para a origem exata, armazenamento persistente, gestão de sessões, limites de requisições, configuração privada e testes de autorização. Configurar apenas uma URL não implementa essas condições.

## Confirmações necessárias antes de dizer que está online

1. O commit enviado existe no remoto correto, sem reescrever o histórico anterior.
2. O job Pages terminou com sucesso e a URL HTTPS responde.
3. Um GLB representativo, uma imagem e um arquivo de cada repositório de acervo respondem com os bytes e SHA-256 esperados; o carregamento WebGL entre origens é testado.
4. O backup privado do `.blend` pode ser baixado e confere com o arquivo salvo.
5. O sincronizador automático só informa sucesso após conferir o remoto; usa exclusão mútua e nunca sobrescreve mudanças remotas por força.
